# tapo-gpv

Розетки Tapo (P100/P105/P110) самі вимикають бойлер за графіком погодинних
відключень — **Черкаська область**, ГПВ по підчергах `1.1`…`6.2`.

Оператор публікує графік кілька разів на добу, і це все, що потрібно знати
системі. Далі вона сама перекладає години відключень у правила на розетці й
пише графік у канал.

[![Python](https://img.shields.io/badge/python-3.11%2B-blue)](https://www.python.org/)
[![License](https://img.shields.io/badge/license-MIT-green)](LICENSE)

Побудовано на [`tapo`](https://github.com/mihai-dinculescu/tapo) — Rust-біндінги,
нативний wheel під Python 3.14.

> **Область застосування.** Парсер читає формат постів
> [`@pat_cherkasyoblenergo`](https://t.me/pat_cherkasyoblenergo). Інші обленерго
> публікують інакше — під них треба правити `outage.py`, решта ланцюга не
> змінюється. Повний перелік меж — у розділі [«Обмеження»](#обмеження).

## Ключова властивість

Розклад (Schedule) зберігається **на самій розетці**, не в хмарі. Правила
продовжують спрацьовувати, навіть коли телефон, роутер або Tapo-хмара офлайн.
P110 зберігає 32 правила.

## Як це працює

```
@pat_cherkasyoblenergo  →  outage.py  →  sync.py  →  розетка
   (текст графіку)         (парсер)     (диф)     ↘  канал
                                                 (пост від бота)
```

Оператор публікує погодинний графік відключень (ГПВ) по 12 підчергах. Кожна
розетка знає свою підчергу; `sync` перекладає її графік у правила «OFF перед
відключенням, ON після» і заливає на пристрій, де вони й живуть.

Щохвилини опитується канал — щоб зловити ревізію графіку або перехід на нову
добу. Пишеться на розетку лише коли набір правил справді змінився, і тоді ж
у канал іде пост із графіком.

Деталі — нижче: [Синхронізація з розетками](#синхронізація-з-розетками) і
[Пости в Telegram-канал](#пости-в-telegram-канал).

## Встановлення

**Вимоги.** Python 3.11+ (розроблено й перевірено на 3.14 — пакет `tapo`
постачається нативним wheel'ом, і для деяких версій Python його може не бути).
Mac або Linux у тій самій мережі, що й розетки. Обліковий запис Tapo — той
самий, під яким розетки додані в застосунку.

```bash
git clone https://github.com/RomanGorbatko/tapo-gpv.git
cd tapo-gpv
python3 -m venv venv
venv/bin/pip install -e .
cp .env.example .env   # заповнити TAPO_EMAIL / TAPO_PASSWORD
```

`.env` у `.gitignore`: там пароль від Tapo й токен бота. У репозиторій іде лише
`.env.example` — з назвами змінних і без значень.

## Використання

Підключись до тієї самої Wi-Fi мережі, що й розетки (не до хотспота iPhone —
там розеток нема).

### 1. Знайти розетки

```bash
venv/bin/python -m tapo_scheduler.discover
```

Три проби поспіль:

| Проба | Що робить | Коли не працює |
|---|---|---|
| mDNS | слухає `_tapo._tcp.local.` | AP isolation, хотспот |
| UDP broadcast | той самий handshake, що робить застосунок Tapo | те саме |
| TCP sweep | стукає в порти 80/443 по всій підмережі | не каже, *який* пристрій відповів |

Якщо mDNS і broadcast мовчать, але TCP sweep щось знайшов — запиши IP в
`TAPO_PLUGS` у `.env` і переходь до кроку 2.

### 2. Підключитись і прочитати стан

```bash
venv/bin/python -m tapo_scheduler.probe 192.168.68.62
# або без аргументів, якщо TAPO_PLUGS заповнено:
venv/bin/python -m tapo_scheduler.probe
```

Показує модель, ім'я, стан, RSSI, наявність енергомоніторингу, поточний
розклад на пристрої та (для P110) видачу енергії.

Приклад:

```
OK  Бойлер основний (P100M) @ 192.168.68.62 — on, rssi -77
    handler      : p110  (device reports P100M)
    energy meter : False
    schedule     : 7/32 rules  ('!' = disabled)
       02:55      every day    -> OFF id=S1
       05:20      every day    -> ON  id=S2
      !21:55      every day    -> OFF id=S3
```

### 3. Керування розкладом

```bash
venv/bin/python -m tapo_scheduler.schedule list
venv/bin/python -m tapo_scheduler.schedule backup
venv/bin/python -m tapo_scheduler.schedule clear --yes
venv/bin/python -m tapo_scheduler.schedule weekly 05:20 on  --days every
venv/bin/python -m tapo_scheduler.schedule weekly 13:55 off --days every
venv/bin/python -m tapo_scheduler.schedule once 13:55 off   # одиничний тест
```

`backup` кладе повний дамп правил у `schedule-backups/`, `clear` без `--yes`
лише показує поточний стан і виходить з кодом 2.

**`--days` обов'язковий по суті, не опційний.** Графік відключень повторюється
щодня, тож кожне правило мусить бути `weekly ... --days every`. `once` не має
днів узагалі — спрацьовує один раз і більше ніколи; годиться лише для
разового тесту. `--days` за замовчуванням `every`, але краще писати явно.

Руками ці правила заливати не треба — це робить `sync`. Команди потрібні, щоб
подивитись стан, зробити бекап або прибрати все перед розбором.

## Особливості бібліотеки `tapo`

Виявились на практиці, не описані в README бібліотеки:

- **`discover_devices` потребує справжніх креденшелів.** Handshake
  автентифікований; з порожнім паролем кожен пристрій повертається як
  `Unauthorized { HASH_MISMATCH }`.
- **`timeout_s` мусить бути `int`**, не `float` — інакше Rust падає з
  `'float' object cannot be interpreted as an integer`.
- **Аксесори непослідовні**: `DiscoveryResultExt` оголошує `ip()`/`model()` як
  методи, а конкретні варіанти несуть `ip` як атрибут. Читати треба з
  перевіркою `callable`.
- **Нікнейм приходить base64-кодованим** (`0JHQvtC5...` → `Бойлер основний`).
- **`get_energy_usage` є не в усіх**: P100M віддає `-1002 UNKNOWN_METHOD`.
  `Plug.energy_usage()` пробує `get_energy_usage` → `get_current_power` →
  `get_device_usage`.
- **Різні одиниці в різних методах**: `get_energy_usage().current_power` — у
  **міліватах**, а `get_current_power().current_power` — у **ватах**. Енергія
  скрізь у Вт·год. `EnergyReading` це нормалізує.
- P100M у discovery класифікується як `DeviceType.Other`, але автентифікується
  через `client.p110()` — handler спільний.
- **`ScheduleRule` не має читабельних атрибутів** — лише фабрики
  (`clock_once`, `clock_weekly`, `sunrise_*`, `sunset_*`, `with_enabled`,
  `with_id`). Те, що виглядає як атрибути, — це Rust `Debug`-репрезентація.
  Тому підтвердження треба будувати з вхідних аргументів, а стан
  перечитувати з пристрою (`schedule_rules()`), а не з об'єкта правила.

## Мережеві граблі

Розетка в **гостьовій мережі** (Deco guest / IoT з ізоляцією) для локального
керування невидима: застосунок Tapo показує «онлайн», бо бачить її через
хмару, але з локальної мережі немає ні ARP, ні ping, ні broadcast. Ознака —
ARP `(incomplete)` при живому IP у застосунку.

Лікується переведенням розетки в основну мережу (або в IoT, якщо прошивка
не ізолює її від основної). Після перепідключення розклад на пристрої
злітає — тримай його в коді як джерело істини.

### Маржа навколо відключення

Вимикати на **5 хв раніше**, вмикати на **20 хв пізніше** — і маржа навмисно
несиметрична:

- **−5 хв OFF.** Розетка має вже бути вимкненою, коли мережа падає, а не
  гинути посеред набору потужності бойлером.
- **+20 хв ON.** Не приєднуватись до кидка, коли все навколо вмикається тієї ж
  секунди, як дали струм.

Маржа не додається до годин, а **розширює вікно**: OFF стає `07:00 − 5 хв`, ON —
`09:00 + 20 хв`. Два відключення, між якими менше ніж `5 + 20` хвилин, зливаються
в одне — немає сенсу вмикатись на проміжок, коротший за маржу. Це не крайній
випадок, а нормальний: оператор видає щільні вікна.

Тому «дзеркальні правила» — це про **стан між** вікнами, а не про самі години:
розетка має струм рівно тоді, коли мережа його не має.

Межі задаються `--lead` / `--lag` (хвилини) в обох CLI.

### Сьогодні й завтра

Оператор іноді публікує графік на завтра звечора, а іноді ні. Тому завжди є два
графіки:

| | Коли є | Що робити |
|---|---|---|
| **на сьогодні** | завжди | заливати на розетку |
| **на завтра** | як пощастить | тримати напоготові |

Правила на розетці повторюються щодня, а графіки двох суміжних діб регулярно
розходяться в тих самих годинах. Тому **на розетці може лежати лише одна доба** —
сьогоднішня. Завтрашня тримається в пам'яті, щоб перехід опівночі був миттєвим,
а не чекав наступного опитування каналу.

Ціна відома: правило «OFF о 23:55» для відключення, що починається о 00:00
**завтрашнього** графіка, буде пропущене. Це безпечніший бік помилки —
зайве вимкнення це дискомфорт, а зайве вмикання під час відключення
нешкідливе (струму в бойлері однаково немає).

### Формат, який парситься

```
1.1 11:00 - 13:00, 17:00 - 19:00, 21:00 - 23:00
```

Два варіанти заголовка — обидва приймаються:

| Заголовок | Коли |
|---|---|
| `Оновлений графік погодинних відключень (ГПВ) на 8 жовтня.` | ревізія |
| `За розпорядженням НЕК «Укренерго» 8 жовтня з 00:00 до 24:00 … (ГПВ).` | перша публікація |

Постів на добу буває кілька — **перемагає найновіший**. Саме на цьому я
спіткнувся: `DATE_RE` вимагав прийменник `на`, тож усі первинні публікації
мовчки не парсились.

`23:00 - 00:00` і `23:00 - 24:00` — це **кінець доби**, не перехід через
північ. Оператор розрізає нічні відключення на півночі, тому вікна завжди
лежать у межах 00:00–24:00.

### Межі методу

- **Тільки плановий ГПВ.** Аварійні відключення публікують без погодинних
  черг — дзеркалити їх правилами неможливо, розетка лишиться там, куди її
  поставив розклад.
- **Пост без тексту** (тільки інфографіка) не парситься взагалі. Тому
  «графік не знайдено» — це привід зберегти попередні правила **й підняти
  тривогу**, а не вирішити, що відключень сьогодні нема.
- **Публічність обов'язкова.** Приватний канал віддає сторінку без постів;
  модуль повертає порожній список, а не помилку.

## Синхронізація з розетками

```bash
venv/bin/python -m tapo_scheduler.sync --dry-run   # показати, що зміниться
venv/bin/python -m tapo_scheduler.sync             # залити один раз
venv/bin/python -m tapo_scheduler.sync --watch     # опитувати канал щохвилини
```

`--dry-run` **читає** розетку (стан і правила) і нічого не пише.

Перед запуском у `TAPO_PLUGS` треба дописати підчергу кожної розетки:

```
TAPO_PLUGS=192.168.68.62:3.1,192.168.68.63:6.2
```

Без підчерги sync **не запускається взагалі** — і не заливає частково. Хибна
черга гірша за відсутню: вона вимикає бойлер у години, коли струм є.

### Що робить один прохід

1. Читає канал, бере **сьогоднішній** графік і (якщо є) завтрашній.
2. Немає сьогоднішнього — **відмова, розетки не чіпаються** (див. нижче).
3. Для кожної розетки будує бажаний набір правил зі своєї підчерги.
4. Порівнює з тим, що вже лежить на пристрої. Однаково — не чіпає.
   Різне — `remove_all_schedule_rules()` і заливає набір заново.
5. Після запису **перечитує** правила з пристрою й падає, якщо вони не ті.

Порівняння перед записом — не оптимізація, а вимога. Sync крутиться щохвилини,
а розклад живе у flash-пам'яті пристрою; перезапис на кожному проході — це 1440
записів на добу.

### Немає графіку на сьогодні

Це **не** «відключень немає». Відсутність неоднозначна: оператор міг
опублікувати саму лише інфографіку, а міг справді нічого не планувати. Тому
типово sync просто відмовляється працювати й лишає на розетці попередні
правила.

Якщо відключень справді немає — це кажуть явно:

```bash
venv/bin/python -m tapo_scheduler.sync --assume-no-outages
```

Тоді правила з розетки **знімаються**: інакше бойлер вимикався б за графіком,
якого немає.

## Пости в Telegram-канал

Після кожного оновлення правил `sync` пише графік у канал — від імені бота.

```bash
venv/bin/python -m tapo_scheduler.notify --check   # перевірити токен і чат
venv/bin/python -m tapo_scheduler.notify "тест"    # надіслати одне повідомлення
```

Налаштування в `.env`:

```
TELEGRAM_BOT_TOKEN=123456:AA...
TELEGRAM_CHAT_ID=-1001234567890
```

Бота створити в [@BotFather](https://t.me/BotFather) і **додати в канал
адміністратором** із правом публікації. Бути учасником недостатньо — `sendMessage`
відповість `chat not found` або `not enough rights`.

Пост виглядає так:

```
📅 Графік на 8 жовтня · черга 5.1

⛔️ Відключення:
09:00–11:00
13:00–15:00
21:00–23:00

🔌 2 tapo-розетки успішно синхронізовано.

Джерело: https://t.me/pat_cherkasyoblenergo/1800
```

Кілька розеток на одній підчерзі дають **одне** повідомлення.

**Переходи розеток у пост не потрапляють.** Вони випливають із відключень за
фіксованим правилом (ті самі 5 хв до й 20 хв після), а шість рядків `08:55 ⛔️`
на екрані телефона відсувають сам графік за межі видимої частини. У пості —
те, навколо чого люди планують день; у логах `sync` — усе інше.

**Пишеться лише коли набір правил справді змінився.** Ревізія, що не зрушила
жодного правила, це не оновлення — пінгу не буде. І навпаки: ревізія, що
повертає попередній набір, пінгується знову, бо стан змінився, хоч текст і
знайомий.

Пам'ять про надіслане лежить у `.state/notify.json`, а не лише в процесі —
інакше перезапущений watcher щоразу заново анонсував би той самий графік.
Файл тримає відбитки стану, не текст.

Три речі, які варто знати:

- **Повідомлення — простий текст, без `parse_mode`.** Український текст графіку
  повний символів, які Markdown і HTML вважають синтаксисом (`–`, крапки в
  `5.1`, `«»`); одна невдало екранована літера — і API відкидає повідомлення
  цілком. Простий текст рендериться завжди.
- **`--dry-run` не пише в канал і не чіпає `.state`.** Інакше репетиція
  змусила б наступний справжній запуск вважати, що графік уже анонсовано, і
  канал тихо лишився б порожнім.
- **Збій постингу не валить sync.** Правила вже на розетці; невдала публікація
  не має їх відкочувати. Але код виходу стає `1`, а в `--watch` рядок про це
  з'являється в лозі.

`--no-notify` заливає правила мовчки.

Токен — це креденшел: хто його має, той постить від імені бота. У `repr` він не
потрапляє (`field(repr=False)`), щоб не текти в трейсбеки й логи. Якщо токен
засвітився — перевипусти його в @BotFather (`/revoke`).

## Структура

```
src/tapo_scheduler/
  net.py       — визначення локальної підмережі та broadcast-адреси
  config.py    — .env: креденшели + інвентар розеток (IP:підчерга)
  discover.py  — пошук розеток у мережі (CLI)
  plug.py      — обгортка над однією розеткою
  probe.py     — підключення й дамп стану (CLI)
  schedule.py  — читання/запис розкладу на пристрої (CLI)
  telegram.py  — читач публічного прев'ю каналу
  outage.py    — парсер ГПВ + дзеркальні правила (CLI)
  notify.py    — постинг у канал через бота (CLI)
  sync.py      — канал → правила → розетки → пост (CLI)
tests/         — pytest, фікстури — справжні постери каналу
  fixtures/    — дослівні шматки постів і реальної HTML-сторінки
```

Поруч: `.env.example` (зразок конфігурації), `LICENSE` (MIT) і `.gitignore`,
який тримає поза репозиторієм `.env`, `.state/` та `schedule-backups/` — усе
це стосується конкретної інсталяції, не коду.

## Тести

```bash
venv/bin/pip install -e '.[dev]'
venv/bin/python -m pytest
```

Фікстури — дослівні шматки справжніх постів і реальної HTML-сторінки. Парсер
крихкий до формулювань оператора (див. вище), тому тести ловлять дрейф
формату, а не лише власні регресії.

Окремо покритий диференціал sync: «правила вже ті — не чіпати» це властивість
коректності, а не оптимізація (див. про flash вище).

## Розгортання

`sync` досить запустити — далі він працює сам:

```bash
cd /шлях/до/tapo-gpv
caffeinate -s venv/bin/python -m tapo_scheduler.sync --watch
```

(Тека може зватись як завгодно — `sync` не залежить від неї. Пакет усередині
зветься `tapo_scheduler`, з підкресленням: у назві теки дефіс, в імені модуля
він неможливий.)

**Окремий сервер для цього не потрібен.** Розклад живе на самій розетці, тож
машина, на якій крутиться `sync`, потрібна лише щоб *ловити нові графіки*.
Засинала вона чи вимкнулась — розетка продовжує працювати за тим, що вже
залите; затримається тільки реакція на ревізію, бо після пробудження `sync`
бере **актуальний** графік, а не «останній побачений».

Що варто врахувати:

- **Машина має бути в тій самій мережі.** Керування локальне, через хмару
  Tapo воно не працює.
- **Сон зупиняє цикл.** `caffeinate -s` (або `pmset`) тримає Mac у неспанні,
  поки той на зарядці; закрита кришка все одно присипляє ноутбук.
- **Логи варто писати у файл** (`2>&1 | tee -a sync.log`) — у `--watch` тихий
  прохід навмисно тихий, тож порожній екран означає «нового графіку не було»,
  а не «все зламалося».
- **Автозапуск** — звичайний `launchd`-агент (`KeepAlive` + `RunAtLoad`).
  Робоча директорія йому не важлива: `.env` читається за абсолютним шляхом від
  кореня проєкту, а не від поточної папки.

## Обмеження

Чесно про те, чого система **не** вміє. Це не список ідей, а межі методу —
щоб не витрачати час на очікування того, чого тут не буде.

Обмеження самого парсера (аварійні відключення, пости без тексту, приватні
канали) — у розділі [«Межі методу»](#межі-методу). Нижче — решта.

**Тільки формат Черкас.** `outage.py` знає два формулювання заголовка, які
використовує `@pat_cherkasyoblenergo`. Інший обленерго — інший парсер; решта
ланцюга (правила, розетки, постинг) не змінюється.

**Одна доба на розетці.** Правила повторюються щодня, а графіки суміжних діб
розходяться, тому вмістити дві доби на один пристрій не можна. Завтрашній
графік тримається в пам'яті й заливається на переході опівночі.

**Правило на межі доби.** Відключення, що починається о `00:00` **завтра**, а
отже вимагає `OFF` о `23:55` сьогодні, буде пропущене. Помилка в безпечний
бік: зайве вимкнення — дискомфорт, зайве вмикання під час відключення
нешкідливе (струму в бойлері однаково немає).

**Одна підчерга на розетку.** Дві розетки на одній підчерзі дають одне
повідомлення й один набір правил; розетка на двох підчергах неможлива за
побудовою.
